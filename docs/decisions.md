# 技術選定・移行の経緯

対象: `my-acronym-app`（アクロニム辞書アプリ）

## 1. Supabase → Neon への移行

**理由（外部制約）**: Supabaseのプロジェクト数上限により、本アプリ専用のプロジェクトを作れず、
既存の別アプリ（`heiwa-sns`）のSupabaseプロジェクトに `acronyms` テーブルだけ間借りしていた。
無関係なテーブル群（`users`/`posts`/`likes`等）とプロジェクトを共有する状態は、無料枠クォータや
セキュリティアドバイザリが両アプリで混ざるリスクがあり、独立したプロジェクトが必要だった。

**移行先としてNeonを選んだ理由**: Vercelとの親和性（Marketplace経由でのProvisioning）と、
サーバーレスHTTPドライバがあること。

**速度目的ではない、という前提**: Neonの無料枠は5分の非アクティブでコンピュートがスケールゼロする。
そのため散発的なアクセスのたびに500ms〜2秒のコールドスタートが発生する。この移行はレイテンシ改善が
目的ではなく、あくまで「別アプリのプロジェクトに間借りしている」という構造的な問題を解消し、
プロジェクトの独立性を確保することが目的である。速度面ではむしろSupabase常時起動プランより
劣化する可能性がある点を明記しておく。

## 2. `@neondatabase/serverless` を選んだ理由

`pg`（node-postgres）ではなく `@neondatabase/serverless` のHTTPドライバを採用。
Vercel Functionsのようなサーバーレス実行環境では、関数呼び出しのたびに新しいTCPコネクションが
張られやすく、`pg`のようなコネクションプール前提のドライバは同時実行数の増加でコネクション枯渇を
起こしやすい。`@neondatabase/serverless` はHTTP経由のfetchベースで、コネクションプールを
アプリ側で管理する必要がなく、この種の枯渇を回避できる。

## 3. 症状の真因はコードではなくDB権限設定だった

検索が0件になる症状は、当初「正規表現の破損」を疑われていたが、実際には無関係だった
（詳細は `diagnosis-acronym-dict.md` 参照）。実機検証の結果、Supabase側で `service_role` に
`acronyms` テーブルへの `SELECT`/`INSERT` 権限（GRANT）が一度も付与されていなかったことが直接
原因と判明した。RLSポリシー自体は正しく存在していたが、RLSはテーブルレベルのGRANTが先になければ
評価対象にすらならないため、Postgres標準の権限エラーが先に返っていた。フロント側がAPIエラーを
無言で空配列にフォールバックする実装だったため、ユーザーからは「検索が何もヒットしない」としか
見えず、実際のエラー内容が不可視だった。

Neonへの移行後は、Neonの接続ロールがテーブル所有者になるため明示的なGRANTが不要になり、
この種の事故は構造的に起きなくなった（`schema.sql` 参照）。

## 4. Gemini → Groq への切替

**理由**: `GEMINI_API_KEY` が未設定（コメントアウト）のまま放置され、AI調査機能が丸ごと
動かない状態だった。ユーザー側で既にGroqのアカウント登録・APIキー発行は済んでいたため、
実装側をGroqに合わせて切り替えた。

**SDKではなくfetchを直接使う設計にした理由**: Groqの呼び出しはOpenAI互換のChat Completions
エンドポイントへの単発リクエストのみで、ストリーミングや複雑なツール呼び出しは行っていない。
専用SDK（`groq-sdk`等）を追加すると依存が1つ増えるだけで、fetchによる素朴な実装で要件を
十分満たせるため、依存を増やさない方針を優先した。

**JSON強制の設計**: `response_format: { type: "json_object" }` を指定し、応答が必ず妥当な
JSON文字列になることをAPI側に保証させている。旧Gemini実装にあった、Markdownコードブロックの
除去や文字列中の `{`/`}` を探す後付けの抽出処理（`parseGeminiJson`）は廃止し、`JSON.parse`
のみで完結する設計にした。

**モデル選定**: `openai/gpt-oss-120b` を使用。Groqが提供するモデル一覧を実際にAPIで確認した
上で選定した（`GET https://api.groq.com/openai/v1/models`）。アクロニムの正式名称・日本語訳・
カテゴリ分類という知識依存度の高いタスクのため、Groqにホストされているモデルの中でも知識・
指示追従性能が高いモデルを優先し、同APIキーで利用可能だった軽量モデル（`openai/gpt-oss-20b`等）
より `openai/gpt-oss-120b` を選んだ。GroqのLPU推論により、大きいモデルでも低レイテンシで
応答が返る。

## 5. Groqモデルを `openai/gpt-oss-120b` にした理由（`qwen/qwen3.6-27b` との実比較）

同じプロンプトで `qwen/qwen3.6-27b` と `openai/gpt-oss-120b` を実際に比較した。
日本語表現の自然さそのものは `qwen/qwen3.6-27b` の方が優れていたが、`japanese_translation`
フィールドの書式が安定しなかった（例: 「シグイント（信号情報）」のようにカタカナ音写と
日本語訳を括弧書きで併記してしまうケースが発生し、定訳のみを1つ返すという制約に従わない
ことがあった）。

「日本語で書け」という言語指定自体はシステムプロンプトの指示で矯正できる問題だが、
「定訳のみを返し、カタカナ音写や括弧書きの併記をしない」という書式の安定性は、
プロンプトを重ねても再現性がなく矯正しきれなかった。`japanese_translation` はUIの表示にも
検索結果一覧にもそのまま使われる値であり、書式が揺れるとアプリの品質に直接影響するため、
表現の自然さより指示追従の安定性を優先し、`openai/gpt-oss-120b` を採用した。

## 6. 参考URLをDBに持たない設計判断

当初はAIに参考URLも生成させてDBに保存する案があったが、以下の理由で採用しなかった。

- **LLMは存在しないURLをもっともらしく生成する**（ハルシネーション）。AIにURLを出力させて
  保存すると、実在しない404リンクがレコードに蓄積し続けることになり、後から検知・修正する
  手段もない。
- **URLは `full_spelling` から機械的に導出できる値であり、DBに永続化する必要がない**。
  Wikipedia検索やGoogle検索のURLは `full_spelling`（と`acronym`）さえあれば都度組み立てられる。
  URLをDBに保存してしまうと、検索先のURL形式が変わった際に既存レコード全件のマイグレーションが
  必要になり、DBに保存しない設計より保守コストが高くなる。

このため、Groqへのプロンプトからはリンク関連の出力指示を外し、AIに求める項目は
`full_spelling` / `japanese_translation` / `description` / `category` の4つのみとした。
リンクは `app/page.tsx` の `DetailCard` 表示時に、`full_spelling`（日本語版Wikipedia検索）と
`acronym` + `full_spelling`（Google検索）から都度生成する方式にし、DBには一切保存しない。
