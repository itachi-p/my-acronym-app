# 技術選定・移行の経緯

対象: `my-acronym-app`（アクロニム辞書アプリ）

## 1. Supabase → Neon への移行

**理由（外部制約）**: Supabaseのプロジェクト数上限により、本アプリ専用のプロジェクトを作れず、
既存の別アプリ（`heiwa-sns`）のSupabaseプロジェクトに `acronyms` テーブルだけ間借りしていた。
無関係なテーブル群（`users`/`posts`/`likes`等）とプロジェクトを共有する状態は、無料枠クォータや
セキュリティアドバイザリが両アプリで混ざるリスクがあり、独立したプロジェクトが必要だった。

**移行先としてNeonを選んだ理由**: Vercelとの親和性（Marketplace経由でのProvisioning）と、
サーバーレスHTTPドライバがあること。

**速度目的ではない、という前提**: Neonの無料枠は5分の非アクティブでコンピュートがスケールゼロする。
そのため散発的なアクセスのたびに500ms〜2秒のコールドスタートが発生する。この移行はレイテンシ改善が
目的ではなく、あくまで「別アプリのプロジェクトに間借りしている」という構造的な問題を解消し、
プロジェクトの独立性を確保することが目的である。速度面ではむしろSupabase常時起動プランより
劣化する可能性がある点を明記しておく。

## 2. `@neondatabase/serverless` を選んだ理由

`pg`（node-postgres）ではなく `@neondatabase/serverless` のHTTPドライバを採用。
Vercel Functionsのようなサーバーレス実行環境では、関数呼び出しのたびに新しいTCPコネクションが
張られやすく、`pg`のようなコネクションプール前提のドライバは同時実行数の増加でコネクション枯渇を
起こしやすい。`@neondatabase/serverless` はHTTP経由のfetchベースで、コネクションプールを
アプリ側で管理する必要がなく、この種の枯渇を回避できる。

## 3. 症状の真因はコードではなくDB権限設定だった

検索が0件になる症状は、当初「正規表現の破損」を疑われていたが、実際には無関係だった
（詳細は `diagnosis-acronym-dict.md` 参照）。実機検証の結果、Supabase側で `service_role` に
`acronyms` テーブルへの `SELECT`/`INSERT` 権限（GRANT）が一度も付与されていなかったことが直接
原因と判明した。RLSポリシー自体は正しく存在していたが、RLSはテーブルレベルのGRANTが先になければ
評価対象にすらならないため、Postgres標準の権限エラーが先に返っていた。フロント側がAPIエラーを
無言で空配列にフォールバックする実装だったため、ユーザーからは「検索が何もヒットしない」としか
見えず、実際のエラー内容が不可視だった。

Neonへの移行後は、Neonの接続ロールがテーブル所有者になるため明示的なGRANTが不要になり、
この種の事故は構造的に起きなくなった（`db/schema.sql` 参照）。

## 4. Gemini → Groq への切替

**理由**: `GEMINI_API_KEY` が未設定（コメントアウト）のまま放置され、AI調査機能が丸ごと
動かない状態だった。ユーザー側で既にGroqのアカウント登録・APIキー発行は済んでいたため、
実装側をGroqに合わせて切り替えた。

**SDKではなくfetchを直接使う設計にした理由**: Groqの呼び出しはOpenAI互換のChat Completions
エンドポイントへの単発リクエストのみで、ストリーミングや複雑なツール呼び出しは行っていない。
専用SDK（`groq-sdk`等）を追加すると依存が1つ増えるだけで、fetchによる素朴な実装で要件を
十分満たせるため、依存を増やさない方針を優先した。

**JSON強制の設計**: `response_format: { type: "json_object" }` を指定し、応答が必ず妥当な
JSON文字列になることをAPI側に保証させている。旧Gemini実装にあった、Markdownコードブロックの
除去や文字列中の `{`/`}` を探す後付けの抽出処理（`parseGeminiJson`）は廃止し、`JSON.parse`
のみで完結する設計にした。

**モデル選定**: `openai/gpt-oss-120b` を使用。Groqが提供するモデル一覧を実際にAPIで確認した
上で選定した（`GET https://api.groq.com/openai/v1/models`）。アクロニムの正式名称・日本語訳・
カテゴリ分類という知識依存度の高いタスクのため、Groqにホストされているモデルの中でも知識・
指示追従性能が高いモデルを優先し、同APIキーで利用可能だった軽量モデル（`openai/gpt-oss-20b`等）
より `openai/gpt-oss-120b` を選んだ。GroqのLPU推論により、大きいモデルでも低レイテンシで
応答が返る。

## 5. Groqモデルを `openai/gpt-oss-120b` にした理由（`qwen/qwen3.6-27b` との実比較）

同じプロンプトで `qwen/qwen3.6-27b` と `openai/gpt-oss-120b` を実際に比較した。
日本語表現の自然さそのものは `qwen/qwen3.6-27b` の方が優れていたが、`japanese_translation`
フィールドの書式が安定しなかった（例: 「シグイント（信号情報）」のようにカタカナ音写と
日本語訳を括弧書きで併記してしまうケースが発生し、定訳のみを1つ返すという制約に従わない
ことがあった）。

「日本語で書け」という言語指定自体はシステムプロンプトの指示で矯正できる問題だが、
「定訳のみを返し、カタカナ音写や括弧書きの併記をしない」という書式の安定性は、
プロンプトを重ねても再現性がなく矯正しきれなかった。`japanese_translation` はUIの表示にも
検索結果一覧にもそのまま使われる値であり、書式が揺れるとアプリの品質に直接影響するため、
表現の自然さより指示追従の安定性を優先し、`openai/gpt-oss-120b` を採用した。

## 6. 参考URLをDBに持たない設計判断

当初はAIに参考URLも生成させてDBに保存する案があったが、以下の理由で採用しなかった。

- **LLMは存在しないURLをもっともらしく生成する**（ハルシネーション）。AIにURLを出力させて
  保存すると、実在しない404リンクがレコードに蓄積し続けることになり、後から検知・修正する
  手段もない。
- **URLは `full_spelling` から機械的に導出できる値であり、DBに永続化する必要がない**。
  Wikipedia検索やGoogle検索のURLは `full_spelling`（と`acronym`）さえあれば都度組み立てられる。
  URLをDBに保存してしまうと、検索先のURL形式が変わった際に既存レコード全件のマイグレーションが
  必要になり、DBに保存しない設計より保守コストが高くなる。

このため、Groqへのプロンプトからはリンク関連の出力指示を外し、AIに求める項目は
`full_spelling` / `japanese_translation` / `description` / `category` の4つのみとした。
リンクは `app/page.tsx` の `DetailCard` 表示時に、`full_spelling`（日本語版Wikipedia検索）と
`acronym` + `full_spelling`（Google検索）から都度生成する方式にし、DBには一切保存しない。

## 7. 略語の複数意味対応 (2026-08-19)

**背景**: 同一略語が領域ごとに異なる意味を持つケース（例: VSPRO はITの
「Virtual Service Provider」であると同時に、ビジネスフレームワーク
「Vision / Strategy / Process / Resource / Organization」でもある）に、
従来はAIが1つの解釈しか返さず、それだけが登録される設計だった。

**UNIQUE制約を `acronym` 単体から `(acronym, full_spelling)` の複合に変更した理由**:
カテゴリではなく `full_spelling` を採用したのは、同一カテゴリ内でも略語が
異なる正式名称を持ちうるため。`acronym` 単体UNIQUEのままだと、そもそも
2つ目の解釈をINSERTすること自体ができない。

**AIに複数解釈を配列で返させる際、JSONのトップレベルをオブジェクトにした理由**:
Groqの `response_format: { type: "json_object" }` はトップレベルが
オブジェクトであることを要求する（配列を直接返すとエラーになる）ため、
`{ "results": [...] }` の形にラップした。件数は1〜4件とし、根拠のない
解釈を無理に埋めさせない指示をプロンプトに含めている。

**一括INSERTを `ON CONFLICT DO NOTHING` にした理由**: AIが返す複数の解釈の
うち一部が既存レコードと重複するケース（再実行時など）を、エラーにせず
黙ってスキップするため。`RETURNING *` により実際にINSERTされた行のみを
APIレスポンスとして返す設計にした。

**AI登録直後の `GET /api/search` 再検索をやめた理由**: 登録前に発行した
同一クエリへの `GET /api/search` が空配列 `[]` を返し、そのレスポンスが
（ブラウザ等の中間層で）キャッシュされたまま登録後の再検索にも使われて
しまい、本番で「登録したのに検索結果が空に見える」事象が発生していた。
これを踏まえ、`POST /api/acronym` の戻り値（実際に登録された行の配列）を
そのままUIに反映する方式に変更し、`GET /api/search` 側にも
`export const dynamic = "force-dynamic"` と `Cache-Control: no-store` を
明示した。前者はNext.js自身のFull Route Cache/静的最適化を無効化する
ためのものだが、それだけではブラウザやCDN等HTTP層のキャッシュは止まらない
ため、後者のヘッダを併用している。

## 8. 手動登録機能の追加 (2026-08-19)

**背景**: 複数意味対応を実装した後も、検索で1件以上ヒットする略語に対しては
「AIで調査して登録」ボタンがそもそも表示されない（`results.length === 0` の
ときしか出ない）ため、既に他解釈で登録済みの略語に追加の解釈を登録する
経路が存在しなかった。実際にVSPRO/SPROがIT用語として先に登録済みだった
ため、ビジネスフレームワーク解釈を追加する手段がなく、この問題が顕在化した。

**手動登録を専用エンドポイント（`POST /api/acronym/manual`）に分離した理由**:
AIの一括登録（`POST /api/acronym`）は複数解釈を前提とした
`ON CONFLICT DO NOTHING` による黙ったスキップが適切だが、手動登録は
人間による単発の意図的な操作であるため、重複時は黙って無視せず
409で明示的にエラーを返すべきという性質の違いがある。挙動が異なる
2つのユースケースを1つのエンドポイントで分岐させるより、責務を分離した。

**UIで「手動登録」導線を常時表示にした理由**: 検索結果の有無に関わらず、
既存解釈と別の意味を追加したい場面（今回のVSPRO/SPROのケース）と、
AI調査でも拾えない語を登録したい場面（社内用語等）の両方をカバーする
必要があるため、`results.length` に依存させず、検索語が2文字以上の間は
常に導線を出す設計にした。

## 9. `?q=` によるディープリンク起動 (2026-08-19)

**背景**: iOSショートカット・共有シート・ブックマーク等、アプリ外から
特定の略語を直接調べたいという入口が複数想定される。それぞれの入口に
個別の実装（ネイティブ連携やカスタムスキーム等）を用意するのはコストが
高い。

**`?q=` を外部入口の共通の受け口にした設計判断**: 入口側は
`https://<app>/?q=<検索語>` というURLを組み立てるだけでよく、
アプリ側の実装は「`/`アクセス時に`q`パラメータを読む」という一箇所に
集約される。ショートカット・共有シート・ブックマークいずれも
「このURLを開く」という共通の操作に還元できるため、入口が増えても
アプリ側の追加実装が不要になる。

**実装**（`app/page.tsx` の起動時`useEffect`）:
- `window.location.search` から `q` を取得し、空なら従来通り入力欄へ
  フォーカスするのみ（通常のブラウザ起動時の挙動を変えない）
- `q`があれば `setQuery(q)` の上で即座に検索を実行する。「手早く
  調べるのが目的の起動経路なので、起動後にもう一度入力させない」
  という前提に基づく
- 検索結果が1件のみの場合はその場で詳細（`selected`）を自動オープンする。
  複数件の場合は一覧から選ばせる（曖昧な場合に誤った解釈を勝手に
  確定させないため）

## 10. 検索結果のポップアップ表示化とフルwidth revert (2026-08-19)

**ポップアップ（オーバーレイ）表示にした理由**: `?q=` 起動で1件だけ
ヒットした場合に詳細へ自動遷移する設計（9章）と対で、背後の検索画面
（入力欄・検索語）をリセットせずに詳細だけを重ねて表示し、一目で読んで
閉じられるようにするため。背景タップまたは✕ボタンで閉じる。

**検索欄を一度縮小し、フルwidthへrevertした理由**: ポップアップ表示の
実装と合わせて検索欄のレイアウトを調整した際、幅を縮める変更を
試みたが、モバイルでの入力しやすさを損なうため `w-full` に戻した
（コミット `8153cd1`）。ポップアップ化そのものとは独立した見た目の
調整であり、機能上の影響はない。

## 11. Enterキーでのショートカット実行 (2026-08-19)

**背景**: 検索用input欄が`<form>`に包まれておらず`onKeyDown`も
未実装だったため、Enterを押しても何も起きなかった。PC利用時に
「AIで調査して登録」ボタンまでマウスを動かす必要があり不便だった。

**発火条件を「結果0件のときのみ」に限定した理由**: 結果が既にある
状態でEnterを押しても何も起きないようにした。これは、既存結果を
見ながら別の略語を続けて調べようとして誤ってEnterを押した場合に、
意図しないAI調査（＝DBへの書き込みを伴う操作）が走ることを防ぐため。
AIボタンの表示条件（`query.length >= 2 && !loading && !searchError &&
results.length === 0 && !aiLoading`）とEnterの発火条件を完全に揃えて
おり、「画面に見えているボタンをEnterで押せる」以上のことはしない。

**IME変換確定のEnterと区別する実装**: `onCompositionStart`/
`onCompositionEnd`でrefフラグを管理しつつ、`onKeyDown`内でも
`e.nativeEvent.isComposing`を追加で見ている。ブラウザによっては
`compositionend`の発火が変換確定用のkeydownより後になるケースがあり、
refフラグ単独では確定Enterを誤って拾ってしまうことがあるため、
両方の判定を併用している。

**手動登録フォームの`onSubmit`挙動は変更していない**: 手動登録フォームは
検索inputとは別の`<form onSubmit={handleManualSubmit}>`であり、
今回のEnterキー実装は検索input（`onKeyDown`）にのみ作用する。フォーム内
のinput/textareaでのEnterは従来通りフォームのsubmitとして扱われる。

## 12. 大文字小文字の扱いの改訂 (2026-08-19)

**当初「強制変換しない」とした理由**: TOCfE（Theory of Constraints for
Education）のような大小混在表記の略語を全大文字化すると、元の表記が
復元できなくなる。これを避けるため、入力表記をそのまま保存・AIへ渡す
設計にしていた（db/schema.sql・decisions.md 各所参照）。

**実運用で判明した問題**: 強制変換しない設計のまま運用した結果、
bbs / seo / tnt のような全小文字入力がそのまま本番DBに登録されて
いた。これらは大小混在の情報を持たない単純な全大文字略語であり、
「そのまま保存」の恩恵（TOCfEのような表記の保持）を受けない一方で、
表記の乱れだけが蓄積していた。既存の該当レコードはSQLで
upper()済み（本タスクでは新たなSQL変更は行っていない）。

**「大文字を1文字も含まない場合のみ全大文字化」に変更した判断**:
判定を「大文字を含むかどうか」の1点に絞ることで、TOCfE/IoT/eSIM/
mRNA/pHのように意図的な大小混在を含む表記は無条件に保持しつつ、
bbs/seoのような単純な全小文字入力だけを救える。正規化は
`lib/normalize-acronym.ts` の `normalizeAcronymCasing` に1箇所だけ
実装し、AI調査（`POST /api/acronym`、Groqへ渡す前とDB保存前の両方）・
手動登録（`POST /api/acronym/manual`、DB保存前）の両経路から呼ぶ。

**ホワイトリスト方式を採らなかった理由**: 「BBS/SEO/TNTのような
既知の全大文字略語を列挙して変換する」方式も検討したが、未知の
略語が来るたびにリストを保守し続ける必要があり、登録経路が
AI調査・手動登録の2つに分かれている状況ではリストの追従漏れが
起きやすい。「大文字を含むかどうか」という表記そのものから判定
できる規則1本の方が、リストの保守なしに同じ目的（全小文字入力の
救済・大小混在表記の保持）を達成できる。

検索側（`lower()`による大小文字を無視した前方一致・重複判定）は
本改訂の対象外。保存値の表記を変えるだけで、既存の検索・重複判定
ロジックには影響しない。

## 13. AI調査のフィルタ基準導入 (2026-08-19)

**背景**: `POST /api/acronym`が返す解釈が実運用でノイズだらけだった。
実例: BSで7件（Broadcast SatelliteとBroadcasting Satelliteの表記
ゆれ重複を含む）、JDで4件、MITで「Made in Taiwan」と「MIT License」、
TNTで「TNT Express」、LPで「Long Play」、FDEでfull_spellingに
「または」を含む2件。原因はシステムプロンプトの件数指定が
「1〜4件」で、AIが件数を埋めようとしていたこと。

**件数を「1〜2件、確信のあるものだけ」に絞った理由**: 件数の上限を
下げるだけでは「無理に埋めようとする」挙動は直らない。上限を
下げた上で「確信のあるものだけ」「1件しか確信が持てない場合は
1件だけ返す」ことを明示し、件数の空きを埋める動機自体を取り除いた。

**除外基準を設けた理由**: 件数を絞るだけでは、Made in Taiwan
（自明語）やMIT License（略語の展開になっていない）のような
個々の低品質な解釈は防げない。実例から共通するパターンを
抽出し、4種の除外基準（自明語／非展開／企業・製品・サービス名／
実在未確認）として明示した。判定基準として「その略語だけを見た
とき、何の略か知らないと意味が取れないか」を渡し、AIが個別の
表現ではなく一貫した基準で判断できるようにした。

**full_spellingの併記禁止・表記ゆれ重複禁止を明示した理由**:
FDEの「または」併記は`full_spelling`という単一の正式名称を
前提とするDB設計（`full_spelling`が重複判定キーの一部）と
そぐわない。またBS実例のBroadcast Satellite/Broadcasting
Satelliteのような表記ゆれは、UNIQUEインデックスが
`lower(acronym), lower(full_spelling)`の完全一致でしか
重複を弾けないため、DB側では防げない。プロンプト側で
「1つの意味につき最も一般的な表記を1つだけ」と明示することで
AI側に防がせた。

**候補選択UIを採らず自動で弾く方針にした理由**: ユーザーに候補を
選ばせる設計も検討したが、選択の手間自体がAI調査機能の
即時性（検索→調査→即登録）を損なう。低品質な解釈を機械的に
判定できる基準（自明語・非展開・企業名等）は明文化できるため、
UIで人間に選ばせるのではなく、プロンプト側の基準で事前に
弾く方が、機能の使い勝手を維持したまま目的を達成できる。

**変更範囲をシステムプロンプトのみに限定した理由**: レスポンス
構造・DBスキーマ・INSERT処理・UIは今回の問題（AIが返す解釈の
質）とは無関係であり、変更するとテスト観点が増え、原因の
切り分けも難しくなる。`MAX_RESULTS`定数（INSERT前の
`slice(0, MAX_RESULTS)`、値4）も変更していない。件数指定は
プロンプト文言としては「1〜2件」に変更したが、これは安全上限
ではなくAIへの指示であり、`MAX_RESULTS`は万一プロンプトの
指示を超えて返ってきた場合の安全上限として従来通り機能する。

## 14. 検索キャッシュ不具合 (2026-08-20)

**症状**: `GET /api/search?q=NPO`等が、DBに該当行が存在するにも
かかわらずHTTP 200で空配列 `[]` を返し続けた。NPO/CIO/PWA/SEC/
SIOP/UIUC/NORAD/UI-UXで再現し、BS/SEO/NGO/IPO/UCLAは正常だった。
再デプロイしても直らなかった。

**正常語と異常語の差**: 文字数でも登録時刻でも境界は引けず、
「その語で初めて検索した時点で、対象行が既にDBに存在していたか
否か」が唯一の分岐点だった。初回検索時点で未登録だった語は、
その時の「0件」という応答がキャッシュに焼き付き、後から行が
登録されても古い0件を返し続けた。

**真因**: `@neondatabase/serverless` はSQL実行のたびに内部で
POSTの`fetch()`を発行するが、これがNext.jsのサーバー内部Data
Cache（fetchキャッシュ）の対象になっていた。`searchAcronyms`
（`lib/db-server.ts`）が発行するSQL文のテキストは常に同一のため、
Data Cacheはこれを同一リクエストとみなし、対象行がまだ
存在しなかった時点の空配列レスポンスをキャッシュキーに紐づけた
まま返し続けていた。

**`force-dynamic`とCache-Controlヘッダでは防げなかった理由**:
`GET /api/search`には`export const dynamic = "force-dynamic"`と
`Cache-Control: no-store`が既に設定されていた（7章）が、これらは
ブラウザ・CDN等リクエストの外側のキャッシュにしか効かない。
Next.js自身がサーバー内部で保持するData Cache（アプリコードが
発行する個々の`fetch()`呼び出しの結果をキャッシュする仕組み）は
別物であり、無効化されていなかった。

**特定方法**: 一時的な診断用APIルート（`/api/diag`、作業完了後に
削除済み）を本番に段階的にデプロイし、同一リクエスト内で複数
パターンのクエリ（フレッシュなクライアント/シングルトン、関数
経由/インライン、SELECT列違い等）を比較。最終的に「SQL文中の
空白を1文字変えるだけ（意味は不変）で0件→正しい件数に直る」
ことを確認し、キャッシュキーがSQL文の完全一致テキストであること
を実証した。

**修正**: `lib/db-server.ts`の`neon()`生成時に
`fetchOptions: { cache: "no-store" }`を明示指定し、Data Cacheを
完全にバイパスするようにした（コミット `24c0301`）。

**3章（Supabaseの`GRANT`漏れ）と同型の事故である**: どちらも
「エラーが表面化せず、空配列という正常に見える応答へ化けるため、
`未登録`と`異常`が区別できない」という共通構造を持つ。3章は
DB権限起因、今回はアプリ層のキャッシュ起因と原因のレイヤーは
異なるが、症状の見え方と発見の難しさは同種である。

**採用しなかった案**: `lib/db-server.ts`の`sql`クライアントを
モジュール単位のシングルトンから呼び出しごとの生成に変える案を
一度適用したが、本番で改善しなかった（実際にはキャッシュの
キーがSQL文のテキストであり、クライアントの生成タイミングとは
無関係だったため）。原因の特定後、この変更は本質的でないと
判断してシングルトンの構成に戻し、`fetchOptions`のみを追加する
最小の修正に絞った。

## 15. SQLファイルを `db/` へ分離 (2026-08-20)

**背景**: `schema.sql` はリポジトリ直下、`seed.sql` は `docs/` 配下と、
Neon復元用の2ファイルの置き場所が揃っていなかった。`docs/STATUS.md`の
ディレクトリ構成ツリーは両方を`docs/`配下と記載しており、実際の
`schema.sql`の位置と食い違っていた。

**配置規則**: 「実行される`.sql`と、読まれる`.md`を混ぜない」。
`docs/`はMarkdownドキュメント（アプリの実行時には読まれず、人間や

SQLファイル（同じく実行時には読まれないが、`.sql`という別種の
実行可能アセット）は`db/`に分離した。拡張子で置き場所が決まる
単純な規則にすることで、判断に迷わず、他プロジェクトにも同じ
規則をそのまま持ち出せる。

**両方とも実行時には読まれない**: `schema.sql`/`seed.sql`は
アプリのビルド・実行時には一切参照されず、Neonプロジェクトが
（無料枠の90日非アクティブ削除等で）失われた際に手動で復元する
ための資産に過ぎない。この性質は移動によって変わらない。

## 16. `POST /api/acronym` への `dryRun` 追加 (2026-08-21)

**背景**: `SYSTEM_PROMPT`（AI調査プロンプト）を検証するたびに、
`POST /api/acronym`がAI調査結果をそのままDBへINSERTするため、
本番DBへ検証由来のレコードが増え続けていた。プロンプト調整の
反復を、本番DBを汚さずに行える手段が必要だった。

**別エンドポイント新設ではなく既存POSTへの分岐にした理由**:
`dryRun`はAI調査そのもの（Groq呼び出し・結果整形）は従来と
完全に同一で、末尾のINSERT有無だけが異なる。別エンドポイントに
すると、Groq呼び出し・レスポンス整形ロジックの二重管理が発生し、
将来`SYSTEM_PROMPT`や整形ロジックを変更した際に片方だけ更新
漏れするリスクがある。`POST /api/acronym/manual`を別エンドポイント
に分離した理由（8章: 重複時の挙動そのものが異なる）とは性質が
違い、今回は「同じ処理の末尾を止めるかどうか」でしかないため、
分岐で足りると判断した。

**認証ガードを付けなかった理由**: 本タスクの目的は
`SYSTEM_PROMPT`検証の反復容易性であり、確認のたびに認証情報を
用意する手間はその目的に反する。既存の`POST /api/acronym`
自体が無認証で公開されている（TODO.md「外部公開の検討」参照）
現状も踏まえ、`dryRun`だけに追加の防御を課しても一貫性がなく、
今回のスコープでは見送った。無認証公開自体の是非はTODO.mdの
既存論点として別途扱う。

**クエリ文字列を真とみなす基準**: `?dryRun=1`または`?dryRun=true`
（大文字小文字・前後空白は許容）のみを真とし、それ以外
（`"0"`/`"false"`/空文字/未指定等）はすべて偽として扱う。
bodyの`dryRun`は`boolean`の`true`のみを真とする
（`"true"`という文字列は真としない。bodyはJSONなので型が
保持されるため、クエリのような文字列限定の曖昧さがない）。

**dryRun時にSELECT（読み取り）は行うと決めた理由**: 今回の
実装時点で`POST /api/acronym`には元々、既存レコードのSELECT
ステップ自体が存在しない（重複判定はDBのUNIQUE制約 +
`ON CONFLICT DO NOTHING`に一任している）。そのため「読み取りは
許可する」という要件は今回のコードには実質的な影響を与えない。
将来この経路に読み取りが追加された場合に備え、方針として
明記だけしておく。

**dryRunレスポンスの形（採用しなかった案を含む）**: 既存の
成功時レスポンスはトップレベルが素の配列（`Acronym[]`）であり、
オブジェクトでラップされていない。トップレベルへ`{ dryRun: true,
results: [...] }`のようにオブジェクトへ変更する案は、
呼び出し元（`app/page.tsx`の`handleAiGenerate`）が
`Array.isArray(data)`で分岐しており、レスポンス形状を変えると
非dryRun時の挙動まで壊しかねないため採用しなかった。代わりに
既存通り配列を返し、配列の各要素（フィールドを追加）に
`dryRun: true`を追加する形にした。`Acronym`型が要求する`id`/
`created_at`は実DB行が存在しないため、`crypto.randomUUID()`と
現在時刻でその場限りの値を仮生成する。フロントエンドでは`id`は
Reactの`key`にのみ使われ、`created_at`はどこにも表示・参照
されていないため、実在しないIDが表示や別操作の起点に混入する
実害はない（`app/page.tsx`調査済み）。

## 17. 逆引き（アクロニム頭文字インデックス）画面の追加 (2026-08-23)

**背景**: 入力フォームを介さず、アクロニムの先頭文字から一覧を
辿れる画面が欲しいという要望。`/reverse`にServer Componentのみで
新設した。

**(a) 分類対象に正式名称ではなくアクロニムを選んだ理由**: この画面は
「略語そのものの先頭文字」から辿る逆引きであり、ユーザーが最初に
目にする/思い出すのは`full_spelling`（正式名称）ではなく
`acronym`（略語）の側であるため。`full_spelling`側の頭文字分類は
別の機能（正式名称からの逆引き）であり、今回はスコープ外とした
（4章「やらないこと」に明記）。

**(b) 数字を個別キーにせず'0-9'に集約した理由**: 数字始まりの
アクロニムはこのDBでは少数派で、'0'〜'9'を個別キーにすると
件数1件だけのキーが並んでインデックスバーが間延びする
（最大28リンクという上限にも関わる）。まとめて1キーにしても
「数字始まりを辿る」という導線自体は損なわれないため、
ナビゲーションの実用性を優先した。

**(c) LIKEではなくキー式の等値比較を採用した理由**: 集計クエリと
一覧クエリが別々の絞り込みロジック（例: 集計は分類式、一覧は
前方一致LIKE）を持つと、実装の些細な差異で両者が食い違い得る
（式がズレても例外は出ない）。同一の`ACRONYM_INDEX_KEY_EXPR`定数
との等値比較に統一することで、集計と一覧が構造的に同じ基準で
絞り込まれることを保証した。LIKEはパラメータ中の`%`/`_`が
ワイルドカードとして解釈される問題もあり、そもそも今回の用途
（分類済みキーとの完全一致）に合わない。

**(d) VIEW・生成列・新規テーブルを採用しなかった理由**: いずれも
DDL（スキーマ変更）を要するが、本タスクはDDL/DMLの実行を禁止
されており（CLAUDE.md）、提示のみ許容されている。また9章
（TODO.md「単一テーブル維持の判断」）で既にテーブル分割・
マスタ化をしない方針が定まっている。JSの文字列定数として
`ACRONYM_INDEX_KEY_EXPR`を1箇所に置き、両クエリがそれを
参照する形にすれば、スキーマに一切手を入れずに「単一の真実」
という目的を達成できる。

**(e) '#'キーを設けた理由**: 記号始まり・全角文字・アクセント付き
文字・トリム後に空になるレコードであっても、逆引きインデックス
のどこかに必ず到達できる状態にするため。'#'を用意しないと、
これらのレコードが集計・一覧のどちらからも見えない
「到達不能なレコード」になってしまう。

**(f) 並び替えをアプリ側で行う理由**: PostgreSQLの既定collationでは
'#'・数字・アルファベットの並び順がDBのロケール設定に依存し、
必ずしも意図した「'0-9' → 'A'〜'Z' → '#'」にならない。
`ORDER BY`をDBに委ねず`lib/reverse-index.ts`の`sortIndexKeyCounts`
で固定配列に基づき並べ替えることで、DB側の設定変更に関わらず
表示順を保証する。

**(g) 2文字目以降の絞り込みを今回見送った理由**: YAGN、かつ
指示（4章）で明示的に対象外とされている。ただし将来の拡張時に
変更点が散らばらないよう、「選択キー→表示レコード集合」の解決
処理を`lib/reverse-index.ts`の`resolveIndexSelection`1箇所に
閉じ込めてある。拡張時はこの関数（と呼び出し元のクエリ呼び出し）
だけを見ればよい設計にした。

**詳細への導線として`?q=`ディープリンクを再利用した理由**: この
アプリには元々、独立した詳細ルーティングが存在しない
（`app/page.tsx`のクライアント側state`selected`によるモーダル
表示のみ）。新たに詳細専用ルートを作ると「既存の辞書画面・API・
スキーマを変更しない」という制約と、既存の`?q=`ディープリンク
機構（9章）という共通の受け口が既にある事実の両方に反する。
そのため`/reverse`の各レコードから`/?q=<acronym>`へリンクし、
既存のディープリンク自動検索・自動オープン機構にそのまま乗せた。

**トリムをクエリ側でも独立に行う理由**: 登録経路
（`POST /api/acronym`、`POST /api/acronym/manual`）は既にJSの
`trim()`で前後空白（全角スペース・NBSPを含む）を除去済みだが
（12章）、それより前に投入された既存データの前後空白除去は
保証されていない。集計・一覧のキー分類がズレると発見しづらい
不具合になるため、クエリ側の`ACRONYM_INDEX_KEY_EXPR`でも
`regexp_replace`により独立してトリムする。全角スペース(U+3000)・
NBSP(U+00A0)は正規表現エスケープの解釈違いに依存させないよう
`chr(12288)`・`chr(160)`のコードポイント指定で組み込んだ
（本番DBに対する動作確認は`.env`値を要するため未実施。
提示したSQL(a)(b)を人間側で実行して確認すること）。

## 19. カテゴリのタグ方式移行に向けた前提整理 (2026-08-24)

**背景**: `tags`/`acronym_tags`テーブルが運用者により本番DBへ
追加され、既存130件全件にis_primaryタグが1件ずつ紐付け済みの
状態で、カテゴリをtext+CHECK制約からタグ方式へ移行する調査・
提案タスクを受け取った。以下2点は今回の調査で確定した方針として
記録する（移行方式自体は`docs/proposals/category-taxonomy.md`を
参照。未確定）。

**(1) `acronyms_acronym_full_spelling_ci_unique`の構成は変更しない
（再確認）**: このUNIQUEインデックスを`acronym`単体から
`(acronym, full_spelling)`の複合にした経緯・理由は既に7章に

2つ目以降の解釈をそもそもINSERTできないという欠点がある）。

基準（`acronym`と`full_spelling`の組み合わせ）とは無関係なため、
このキーの構成には一切手を入れない。将来のセッションがタグ移行の

登録され得る（例: "BS"の7件中2件は衛星放送の正式名称の語尾

**登録経路（プロンプト・INSERT前の整形処理）側**であり、

## 20. カテゴリのタグ方式移行の実装 (2026-08-26)

**背景**: 19章で前提整理・`docs/proposals/category-taxonomy.md`で
提案していたタグ方式移行を、運用者が本番DBへ19タグ（旧6値→7表示
グループへ再編）・`acronym_relations`テーブル追加・全101件への
backfill・`acronyms_category_check`削除を適用した状態を前提に
実装した。以下5点を判断として記録する。

**(1) 複合カテゴリ名（「ビジネス・経営」等）を原子タグへ分解した
理由**: 旧方式は`acronyms.category`が単一値のtext列だったため、
「1レコードにつきカテゴリは1つしか選べない」という制約から、
複数の関心事をあらかじめ1つの複合名（例:

`acronym_tags`により1レコードが複数タグを持てるようになったことで、
この複合名という妥協が不要になった。「経営」と「組織・人事」を
別々の原子タグとして持たせられるため、複合名特有の曖昧さ
（あるレコードが経営寄りなのか組織・人事寄りなのか、複合名では
判別できない）も解消される。

**(2) 分類層（`tags.name`）と表示層（`tags.display_group`）を
分離した理由**: 旧TODO.md「カテゴリの追加」が抱えていたトレード
オフは「分類を細分化するとUIのタブ数が増え、モバイルでのレイアウトが
崩れる、あるいはプルダウン化を迫られる」というものだった
（タグ＝UIボタンが1:1で結びついていたため）。`display_group`という
緩衝層を挟むことで、原子タグ（分類の細かさ）とUIボタン数
（7個で固定）が独立変数になった。タグを何十個追加しても
`display_group`が増えない限りUIのボタン数は変わらないため、
このトレードオフは構造的に解消される。

**(3) 複合ユニークキーを`(acronym, full_spelling)`のままにした
理由（19章の再確認）**: 今回の移行はカテゴリの持ち方を変えるだけで、
重複判定の基準とは無関係。同一略語が分野違い・分野内の両方で
複数の正式名称を持ちうる実例（CRM, GCP, TOC, LLM, LP, SEC, MIT,
BS, JD, EV, IRA, PPAP, SIOP, RAS, TNT等）が実在するため、単一
カラムUNIQUEへ戻すと2件目以降の解釈がそもそもINSERTできなくなる。
このキーは変更していない（実装時に変更するコードも書いていない）。

**(4) 関連リンクをホモニム（自動・クエリ時）と概念的関連
（手動・専用テーブル）に分けた理由**: 「同じ略語の別の意味」
（ホモニム）は、`(acronym, full_spelling)`複合UNIQUEの設計上すでに
DBに存在するデータ（同一`acronym`・別`full_spelling`の行）から
`lower(acronym)`の等値クエリだけで導出できる。新規データ投入は
一切不要で、既存の重複略語すべてに遡及的に効く
（`lib/db-server.ts` `getAcronymRelated`のhomonymsクエリ）。一方
「概念的に関連するが略語が異なる」関係（例: MAD⇔SIOP）は
`acronym`列からは導出しようがなく、人間が関係の存在を判断して
明示的に登録する必要があるため、別テーブル`acronym_relations`
（手動運用、今回は追加投入していない）に分離した。自動導出できる
ものとできないものを同じ仕組みで扱おうとすると、後者のために
前者まで手動登録が必要になってしまうため、この分離は必須と判断した。

**(5) NeonのHTTPドライバでは複数文トランザクションが使えないため、
CTEで単一SQL文にまとめて二重書きのアトミック性を確保した判断**:
`@neondatabase/serverless`のHTTPドライバは`BEGIN`/`COMMIT`で
くくった複数文のトランザクションを素直に扱えない（前セッションで
確認済みの制約、今回のタスク前提として引き継いだ）。`acronyms`と
`acronym_tags`という2テーブルへの書き込みをアトミックに行うため、
`WITH ins AS (INSERT INTO acronyms ... RETURNING ...), tag_ins AS
(INSERT INTO acronym_tags ... RETURNING ...) SELECT ... FROM ins`
という単一SQL文のCTEにまとめた（`lib/db-server.ts`
`insertOneAcronymWithTags`）。実装時に踏んだ落とし穴を記録する:
同一WITH文内のサブステートメントは全て同一スナップショットで実行
されるため、`tag_ins`が挿入した行を同じ文の中で`acronym_tags`
テーブルを素朴に読み直しても見えない（PostgreSQL文書7.8.2
"they cannot see one another's effects on the target tables"）。
そのため返り値のタグ情報は、挿入直後のテーブルを読み直す相関
サブクエリではなく、INSERTのソースに使った`tag_rows`CTE自体を
`tags`と結合して組み立てている。また、複数解釈（AI一括登録で
最大4件）をこの単一行CTEで1件ずつ順に実行する設計にしたため、
以前の単一INSERT文（複数VALUES行）による一括書き込みと異なり、
**複数行全体としての原子性（全行成功/全行失敗）は無くなった**
（行単位ではアトミック）。タグの対応関係を保ったまま複数の
acronym行と複数のacronym_tags行をまとめて書く単一SQL文が組めな
かったための妥協。`MAX_RESULTS`が4件程度に抑えられていることも
あり許容している。

## 21. カテゴリ（表示グループ）ボタンを固定列数でなく折り返しにした理由 (2026-08-26)

**背景**: トップ画面のカテゴリボタン行（`app/page.tsx`）が
`overflow-x-auto`（`flex-wrap`なし）だったため、375/390/768/1280px
のいずれの幅でも内部横スクロールが発生し、後方のボタン（テック・
学術・その他）が画面外に押し出されて隠れる不具合があった。
1280pxでも発生していたのは、ボタン行が`max-w-lg`コンテナ内にあり
実効幅が最大でも480px程度で頭打ちになるため（PC幅を広げても
解消しない）。Playwrightで`document.documentElement`の
`scrollWidth`だけでなく、`overflow-x:auto`要素自身の
`scrollWidth`と`clientWidth`の差分も走査するスクリプトを書いて
実測し、この1箇所のみが原因であることを確認した上で修正した。

**なぜ固定のグリッド列数（`grid-cols-N`等）にしなかったか**:
表示グループは`tags.display_group`から動的に生成される
（19章・20章参照）。現在は7個だが、タグの新設・統合に伴い
`display_group`自体が増減する可能性がある（20章の設計目的が
「タグを増やしてもUIのボタンは増えない」ことだったとしても、
`display_group`という表示層そのものの再編は起こりうる）。グリッド
列数をハードコードすると、グループ数が変わるたびにレイアウトの
見直しが必要になる。`flex flex-wrap gap-2`（`app/reverse/page.tsx`
の`IndexBar`が既に同じパターンを採用しており、実績がある）へ
統一することで、ボタン数に関わらず1行に収まらない分は自動的に
次の行へ折り返され、コード変更なしに任意の個数へ対応できる。

**タップ領域の同時対応**: 同じ修正のついでに、カテゴリボタン・
`/reverse`のインデックスキー・関連用語ボタン・副タグ選択ボタン・
閉じるボタンなど、縦方向のpaddingが小さかった（`py-1`/`p-1`）
インタラクティブ要素のpaddingを広げた（`py-1.5`〜`py-2`/`p-2`）。
配色・フォント・既存レイアウトの構造自体は変更していない
（padding調整のみ）。

**e2eテストとの衝突**: `app/reverse/ResultBrowser.tsx`の
アコーディオン行のacronym表示`div`は、`e2e/reverse-lookup.spec.ts`
が`div[class="font-bold text-indigo-700 dark:text-indigo-300"]`
という完全一致セレクタで依存している。このdivに長文防御用の
`break-words`を追加すると、class属性の完全一致が崩れテストが
壊れることが実測（`npm run test:e2e`の失敗）で発覚したため、
この1箇所のみは意図的にクラスを変更していない（acronym自体は
短い文字列のため折り返し防御の優先度は低いと判断）。他の
japanese_translation・full_spelling・description・タグピル・
関連用語ボタン等には`break-words`（+flexコンテキストでは
`min-w-0`）を防御的に追加した。実データ（`SWIFT`の正式名称、
`USA PATRIOT Act`等）では元々スペース区切りのため折り返し自体は
発生していたが、空白を含まない英数字の連続がある場合に備えた
予防的対応。

## 22. 登録候補フィルタリングの実装 (2026-08-26)

**背景**: Groqの調査結果が無条件・複数同時にDBへINSERTされる設計
だったため、低価値レコードが混入し人手での削除が発生していた
（19章で記録した"BS"表記ゆれ重複等の一部はこの経路由来）。運用者が
`rejected_candidates`テーブルと`acronyms_normalized_unique`
（表記ゆれを正規化したユニーク制約）を本番DBへ追加済みの状態で、
INSERT前に候補を検証し基準に合わないものを拒否する仕組みを実装した。
以下3点を判断として記録する。

**(1) 定期的な掃除ではなく入口で弾く方式を選んだ理由（コストが低い）**:
低価値レコードへの対処には大きく2つの方式がある。(a)事後的に
棚卸しして削除する（TODO.mdの「低価値レコードの掃除」がこれに
あたる、table-cleanup Skillで別途実施予定）、(b)登録時点(INSERT前)
で弾く。(a)は一度紛れ込んだレコードを人間が個別に判断して消す
作業が発生し、件数が増えるほどコストが線形に増える。(b)は
INSERT前の1回の判定で完結し、判定基準さえ整えれば以降のコストが
増えない。今回追加した3系統の判定（機械判定D1/D2/D5、Groq自身への
採用基準の埋め込み、正規化ユニーク制約によるDB側の最終防御）は
いずれも(b)の入口側に位置し、事後掃除に依存する部分を減らす
ことが目的である。事後掃除自体は完全に不要にはならない
（判定基準を後から追加・変更した際に過去分は残るため）が、
発生源を絞ることで棚卸しの対象を減らせる。

**(2) 正規化ユニークインデックスで表記ゆれだけを弾き、別概念の
同一略語は通す設計にした理由**: `acronyms_normalized_unique`は
`(lower(acronym), lower(regexp_replace(full_spelling,
'[^a-zA-Z0-9]','','g')))`に対する制約であり、`full_spelling`から
英数字以外（スペース・ハイフン等）を除去してから比較する。これは
「Non-Profit」と「Nonprofit」のような**同一概念の表記ゆれ**だけを
狙い撃ちにするためで、`acronyms_acronym_full_spelling_ci_unique`
（変更禁止、7章・19章参照）が保証している「同じ略語で意味が異なる
レコードは複数存在してよい」という設計とは矛盾しない。表記ゆれ
判定を`full_spelling`の完全一致ではなく正規化後の一致にしたのは、
13章で導入したGroqへの表記ゆれ禁止指示（プロンプト側の対策）を
すり抜けた場合の最終防御線として機能させるため。二重の防御
（プロンプトでの指示＋DB制約）にすることで、Groqの応答が指示に
従わなかった場合でもDBレベルで確実に弾ける。

**(3) 拒否を削除ではなくログとして残す理由（誤爆の検証が可能に
なる）**: 拒否した候補は`rejected_candidates`に`reason_code`
（D1/D2/D3/D5/LIMIT）と`reason_detail`付きで記録し、`acronyms`から
削除する対象自体をそもそも作らない（そのため「削除」という概念が
発生しない）。この設計により、5-Bで運用者が確認する「正当な略語が
誤って弾かれていないか」の検証が可能になる。もし判定を素通りさせて
記録も残さなければ、正当な候補が誤って弾かれた場合にその事実
自体に気づく手段がない。`reason_code`を分類しておくことで、
特定の判定（例:D2の自己言及判定が誤検知しやすい等）が判明した
場合に、許可リストへの追加や判定ロジックの見直しを
データに基づいて行える。ログの書き込み自体が失敗しても主フロー
（候補の登録可否判定・INSERT）は止めない設計にした
（`lib/db-server.ts` `recordRejectedCandidates`のコメント参照。
診断用の副作用が本来の登録処理を巻き込んで失敗させるべきではない
という判断）。

**実装上の技術的注記**: `acronyms_normalized_unique`は
`insertOneAcronymWithTags`のCTE内`ON CONFLICT`節が対象とする索引
（`(lower(acronym), lower(full_spelling))`、旧ci_unique用）とは
別の索引のため、違反時は`DO NOTHING`で吸収されず通常のPostgres
例外（`23505`）として投げられる。この違反は候補1件ごとの
INSERT呼び出し（`insertOneAcronymWithTags`を直接、候補単位で
try/catch）で捕捉しており、複数候補をまとめて呼ぶ`insertAcronyms`
（1行でも例外が出るとバッチ全体を中断し、既に成功していた候補の
情報も失われる）は使っていない。手動登録（`POST /api/acronym/manual`）
でも同じ索引の違反が同様に無捕捉のまま500になっていた点を
インシデンタルに修正し、既存の409重複メッセージへ正しくマッピング
した（新しい判定基準の追加ではなく、既存の「重複」概念を新しい
索引にも正しく適用しただけの是正）。

## 23. ヘルプページを単一マークダウンで管理した理由 (2026-08-26)

**背景**: `/help`を追加するにあたり、文言修正のたびにコード変更・
レビュー・デプロイのフルサイクルを要する状態を避けたいという要求
だった。以下2点を判断として記録する。

**(1) 単一マークダウンファイル管理にした理由（文言修正にコード変更を
伴わせないため）**: ヘルプの内容を`app/help/page.tsx`にJSXとして
直接書く選択肢もあったが、その場合は文言の1文字修正であっても
TSXファイルの変更・型チェック・レビューを要する。`content/help.md`を
唯一の情報源とし、`app/help/page.tsx`はこのファイルを読み込んで
レンダリングするだけの薄い層にすることで、文言修正は
マークダウンファイルの編集だけで完結する。画像も同様に
`public/help/`配下のファイル差し替えだけで反映されるようにした
（`app/help/page.tsx`はファイル名を直接ハードコードせず、
マークダウン内の画像パス表記をそのまま解釈する）。

なお、この静的レンダリングは`next build`時点のスナップショットで
あるため、Vercel本番環境で`content/help.md`の変更を反映させるには
**再デプロイが必要**（コード変更は不要、コンテンツ変更のみで
再デプロイをトリガーすれば良い）。これは3-1で明示された
「ビルド時に静的にレンダリングする。クライアントからのfetchは
しない」という要求の直接の帰結であり、欠陥ではない
（クライアントfetch方式にすれば再デプロイ不要にできるが、
ページ表示のたびにファイル読み込みが発生し、静的配信の利点を
失う。今回は要求通り静的レンダリングを選んだ）。

**(2) 信頼できるファイルであっても生HTMLを無効にした理由**:
`content/help.md`は運用者が管理する信頼できるファイルであり、
外部入力ではない。しかし生HTML解釈を有効にする経路
（`rehype-raw`プラグイン等の追加）を一度作ってしまうと、将来
このファイルの入力元が変わった場合（例: 運用者以外の投稿を
許可する、CMS経由にする等）に、生HTML経路が残ったまま
危険な変更になりうる。今回採用した`react-markdown`は
デフォルトで生HTMLタグをただの文字列としてエスケープ表示する
（`rehype-raw`を追加しない限り解釈しない）。この既定動作を
そのまま維持し、意図的に有効化する追加パッケージ・オプションを
一切導入しないことで、「今は安全」ではなく「経路自体が無い」
状態を保った。

**マークダウンライブラリの選定（react-markdown）**: Reactの
コンポーネントツリーとしてレンダリングする方式のため、
`dangerouslySetInnerHTML`を経由しない。デフォルトエクスポートの
`Markdown`コンポーネントは同期的（内部でReact Hooksを使わない）
であり、Server Component内でそのまま呼び出せる
（同パッケージの`MarkdownHooks`は非同期プラグイン対応のため
`useState`/`useEffect`を使いクライアント専用になるが、今回は
使っていない）。画像・見出し・リンク等のレンダリングは
`components`propで独自のTailwindクラスを当てており、
`@tailwindcss/typography`等の追加パッケージは導入していない
（「マークダウン以外にUIライブラリ・CSSフレームワークを
追加しない」という制約を、react-markdown 1点の追加で満たすため）。

## 24. 短すぎる略語(2文字以下)の判定を機械判定にも置いた理由 (2026-08-26)

**背景**: 22章の登録候補フィルタリング実装時点では、「略語が2文字
以下は原則対象外（例外: BS/PL/LP/EV/pH）」というルールをGroqへの
プロンプト（採用基準）にのみ記載しており、コード側の判定
（D1/D2/D3/D5）には含めていなかった。運用の中で、この設計だと
Groqがプロンプトに従わなかった場合に挙動が再現しない
（同じ略語「TI」で検索しても、ある時は拒否されずそのまま登録され、
別の時はGroq自身が「該当なし」を返す、といった非決定的な結果に
なりうる）ことが判明したため、A1として機械判定に追加した。

**プロンプトだけでなく機械判定にも置いた理由**: LLMへの指示は
本質的に「お願い」であり、遵守を保証しない。22章で既に
D1/D2/D3/D5をコード側の決定的な判定として実装していたのと同じ
理由で、A1も文字数という機械的に検証可能な条件である以上、
プロンプト側の指示だけに依存せずコード側でも決定的に弾くべきと
判断した。これにより「TI」のような候補は、Groqの応答内容に
関わらず常に同じ結果（A1拒否）になる。許可リスト
（BS/PL/LP/EV/pH、大文字小文字を区別しない）はD1/D2の例外リストと
同じ`CANDIDATE_ALLOWLIST`（`lib/candidate-filter.ts`）にまとめて
あり、後から候補を追加する場合の変更箇所を1つに保っている。

**手動登録経路には適用しない理由**: A1を含む機械判定
（`runMachineChecks`）は、AIが無条件・大量に候補を生成することへの
暴走抑制が目的であり（22章参照）、人間が1件ずつ意図して入力する
手動登録（`POST /api/acronym/manual`）にはこの前提が当てはまらない。
2文字の略語であっても、人間が「これは実在し登録する価値がある」と
判断して手動登録する分には制限する理由がないため、
`lib/candidate-filter.ts`は手動登録の経路からは呼び出していない
（`app/api/acronym/manual/route.ts`はこのモジュールをimportしない）。
D1/D2/D3/D5についても同様に手動登録には未適用のままとした
（22章時点からの現状維持。今回の作業指示の対象外のため変更していない）。

**UIでの拒否理由の出し分け**: A1による拒否は「Groqが見つけられ
なかった」のではなく「意図的に制限している」ことが理由であるため、
他の拒否理由（D1/D2/D3/D5/LIMIT）と同じ簡潔な通知では
「AIが仕事をしていない」という誤解を招く。`POST /api/acronym`の
レスポンスに`rejectedReasonCodes`を追加し、`'A1'`が含まれる場合のみ
専用の説明文（自動登録を制限している理由）と、手動登録フォームを
直接開くリンクを表示するようにした。A1はacronym（1回の検索で
全候補が共有する値）だけに依存する判定のため、1回の検索内で
A1とそれ以外の理由が混在することは起こらない
（A1に該当すれば全候補が同じ理由で拒否される）。

## 25. ヘルプ画像のレターボックス解消 (2026-08-26)

**背景**: `/help`の画像（`app/help/page.tsx`の`img`オーバーライド）が
`w-full max-h-[70vh] object-contain`を併用していたため、box幅が
ラッパー実効幅（`max-w-lg`由来の480px）に固定され、`max-h-[70vh]`
による高さ制約と組み合わさった結果、縦長のスクリーンショット
（346×750相当）が実寸より大幅に縮小されて箱の中央に描画され、
左右に大きな空白（box 480×491pxに対し絵226×491px、空白254px＝
枠面積の53%）が生じていた。DevToolsでのcomputed style実測を
先に行い、CSSの組み合わせが原因であることを画像ファイルや
markdownの中身を疑う前に特定した上で対処した。

**採用: `w-full`を外し、画像の実寸に枠を密着させる**:
`w-full`（width明示）を削除すると、Tailwind preflightの
`height: auto`とTailwindの`max-h-[70vh]`との組み合わせにより、
幅が画像の縦横比から逆算される（高さがmax-heightで頭打ちに
なった時点で、幅もその高さに応じた比率に再計算される、という
CSSの置換要素サイズ決定の挙動）。結果としてboxが絵の実寸と
一致し、レターボックスが解消する。中央寄せは`mx-auto`で維持した。
box幅とmax-heightがぴったり一致した時点で寸法差が無くなるため、
`object-contain`は不要になり削除した（このimg以外に使用箇所が
無いことを確認済み）。

**不採用: box幅を維持したまま`object-cover`で埋める案**:
`object-cover`は箱全体を絵で埋めるが、縦長のスクリーンショットを
横長寄りの箱に合わせて引き伸ばす/切り出すため、上下（手順画面の
上部・下部のUI要素）が切れて手順が読み取れなくなる。ヘルプの
スクリーンショットは操作手順を伝えるための実用画像であり、
装飾目的の写真とは異なり全体が見えることが必須のため不採用。

**不採用: レイアウト全体のレスポンシブ化（グリッド化等）**:
`max-w-lg`固定の1カラム構成をやめてPC幅でグリッド表示にすれば
ページの縦の長さは短縮できるが、影響範囲がヘルプページ内に
留まらず、検索UI・逆引き画面を含むアプリ全体の1カラム設計
（PWAとしての設計判断、前タスクまでのレスポンシブ対応の前提）の
見直しになる。今回の作業指示のスコープ（レターボックス解消）を
超えるため、別タスクとして切り出した（TODO.md参照）。

**記録すべき原則**: 表示異常を調査する際は、まずCSSが実際に
どう適用されているか（computed style）をDevTools等で確認してから、
画像ファイルやmarkdownの中身を疑う順序にする。今回の一連の調査
では、実際の原因は`w-full`と`max-h-[70vh]`と`object-contain`という
**クラスの組み合わせ不整合**であり、画像ファイル（11枚とも
346×750で正常）にもmarkdown（画像パスは`/help/*.png`で正しく配信）
にも問題は無かった。表示が崩れているように見えても、原因が
コンテンツ側にあるとは限らない。

## 26. セッション中断からの復旧: ヘルプページPC最適化ほか (2026-08-27)

**背景**: 前回のCLIセッションが回線問題により長時間（40分超）
応答不能になり、強制的に再起動した。その際の作業がworking tree上に

ビルド・lint・レスポンシブ計測で壊れていないことを確認した上で
コミットに整理した。

**(a) ヘルプページのPC向けレイアウト最適化**: TODO.md（25章参照）で
別タスクとして切り出していた項目。1024px以上でのみ`.help-article`を
CSS Grid化（`grid-template-columns: repeat(3, 1fr)`）し、画像単体の
段落（`p:has(> img:only-child)`）だけをグリッドセルに収める。
