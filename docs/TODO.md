  （複数候補の同時登録を実装した後も、拾いきれないケースは残る）

- アプリ外からの入口整備
  背景: 調べたい略語に遭遇 → アプリ起動 → 手入力、というステップを
  削りたい。当初ホーム画面ウィジェットでの直接入力を検討したが、
  iOS・Androidともにウィジェットはテキスト入力ビューを持てないため
  技術的に不可能と判明（ネイティブ実装でも同様）。代替として以下を計画。

  方式A: ショートカットが ?q= 付きURLを開く
  - ホーム画面アイコンから起動 → 入力を要求 → アプリで結果表示
  - 共有シート経由: 選択したテキストを q として渡す
  - 実装済みの ?q= をそのまま使うため、アプリ側の追加実装は不要

  方式B: ショートカット内でAPIを直接呼び、結果をその場に表示
  - ブラウザに遷移せず、読んでいたページのまま結果を確認できる
  - 0件時は POST /api/acronym を叩いてAI調査+登録まで行う
  - APIレスポンスがショートカットの「結果を表示」で読みやすい形か
    要検討。必要なら整形用のレスポンス形式を追加する

  方式A・Bの選択基準:
  入口ごとに体験を揃える必要はない。目的はステップ数の削減であり、
  統一そのものではない。
  - 既存レコードの検索: 最短で結果が出ればよい。方式Bが向く
  - AI調査+登録: 結果の確認と登録の可否判断が要る。方式Aが向く場合がある
  - 手動登録: フォーム入力が必須のためアプリ起動が前提。入口整備の対象外
  統一を優先して手数が増えるなら本末転倒であり、その場合は分けたままにする。

  iOS制約のメモ:
  - manifest.json の share_target は iOS Safari で機能しない
    （Baseline未達、iOSではPWAがURLを捕捉できない）。共有シート導線は
    ショートカットで実現する
  - Androidを対象にする場合は share_target が使えるため、その際に
    追加検討

- force-dynamicがData Cacheを無効化しなかった正確な理由（未調査）
  `export const dynamic = "force-dynamic"` は本来ルート内の
  `fetch()`をキャッシュ無効化するはずだが、`@neondatabase/serverless`
  が発行する内部fetch()には効かなかった（decisions.md 14章）。
  実害は`fetchOptions: { cache: "no-store" }`の明示指定で解消済みの
  ため低優先。Next.jsのバージョン依存の挙動か仕様の誤解かは未確認

- キャッシュ焼き付き期間中に重複登録された可能性のあるレコードの棚卸し
  検索キャッシュ不具合（decisions.md 14章）により「0件」が古い
  キャッシュのまま返っていた期間、実際には既に登録済みの語を

  UNIQUE制約をすり抜けている）登録されているのはこれに該当する
