`lower()`比較でも別レコードとして扱われるためこの制約では弾けず、
13章の対策はプロンプト側のみ。本項目（MAX_RESULTS）は
この「無条件複数登録」という設計の一部であり、下記「未着手」の
関連項目とあわせて検討すること。

### 7. 文字正規化と特殊文字の扱い
RAG: Retrieval‑Augmented Generation のハイフンが U+2011。
NFKC 正規化で寄せるか、許可文字を制限するか。実害が出ていないため低優先。

### 8. 検索クエリのインデックス利用確認
lower(acronym) の前方一致が UNIQUE 複合インデックスを使えているか
EXPLAIN で確認する。現状のボトルネックは件数ではなく Neon の
コールドスタート（500ms〜2秒）であり、実測するまで要否は決まらない。

### 9. 単一テーブル維持の判断（記録のみ）
テーブル分割はしない。繰り返される値は category のみで、
6種類の固定値。CHECK制約で担保済み。マスタ化しても JOIN が
増えるだけで得がない。decisions.md に記録すること。

- db/seed.sql の再エクスポート
  背景: 本番DBの既存レコードのうち全小文字だったacronym（bbs/seo/tnt等）
  はSQLでupper()済みだが、db/seed.sqlはその修正前の状態のまま
  （本タスクでは再エクスポートしていない）。SQLでの修正は
  decisions.md 12章参照。次にseed.sqlを触る際、本番Neonの現状データで
  再エクスポートし、差分を解消すること

- 検索結果が期待と違った場合の再調査導線
  現状、未登録語は1回のAI調査結果が無条件に登録される。
  「思っていた意味と違う」場合にAIへ別解釈を要求する手段がない。
  手動登録機能により「気づいた側から自分で直接登録する」応急的な
  回避は可能になったが、AI側に再調査させる導線そのものは未実装
  （複数候補の同時登録を実装した後も、拾いきれないケースは残る）

- アプリ外からの入口整備
  背景: 調べたい略語に遭遇 → アプリ起動 → 手入力、というステップを
  削りたい。当初ホーム画面ウィジェットでの直接入力を検討したが、
  iOS・Androidともにウィジェットはテキスト入力ビューを持てないため
  技術的に不可能と判明（ネイティブ実装でも同様）。代替として以下を計画。

  方式A: ショートカットが ?q= 付きURLを開く
  - ホーム画面アイコンから起動 → 入力を要求 → アプリで結果表示
  - 共有シート経由: 選択したテキストを q として渡す
  - 実装済みの ?q= をそのまま使うため、アプリ側の追加実装は不要

  方式B: ショートカット内でAPIを直接呼び、結果をその場に表示
  - ブラウザに遷移せず、読んでいたページのまま結果を確認できる
  - 0件時は POST /api/acronym を叩いてAI調査+登録まで行う
  - APIレスポンスがショートカットの「結果を表示」で読みやすい形か
    要検討。必要なら整形用のレスポンス形式を追加する

  方式A・Bの選択基準:
  入口ごとに体験を揃える必要はない。目的はステップ数の削減であり、
  統一そのものではない。
  - 既存レコードの検索: 最短で結果が出ればよい。方式Bが向く
  - AI調査+登録: 結果の確認と登録の可否判断が要る。方式Aが向く場合がある
  - 手動登録: フォーム入力が必須のためアプリ起動が前提。入口整備の対象外
  統一を優先して手数が増えるなら本末転倒であり、その場合は分けたままにする。

  iOS制約のメモ:
  - manifest.json の share_target は iOS Safari で機能しない
    （Baseline未達、iOSではPWAがURLを捕捉できない）。共有シート導線は
    ショートカットで実現する
  - Androidを対象にする場合は share_target が使えるため、その際に
    追加検討

- force-dynamicがData Cacheを無効化しなかった正確な理由（未調査）
  `export const dynamic = "force-dynamic"` は本来ルート内の
  `fetch()`をキャッシュ無効化するはずだが、`@neondatabase/serverless`
  が発行する内部fetch()には効かなかった（decisions.md 14章）。
  実害は`fetchOptions: { cache: "no-store" }`の明示指定で解消済みの
  ため低優先。Next.jsのバージョン依存の挙動か仕様の誤解かは未確認

- キャッシュ焼き付き期間中に重複登録された可能性のあるレコードの棚卸し
  検索キャッシュ不具合（decisions.md 14章）により「0件」が古い
  キャッシュのまま返っていた期間、実際には既に登録済みの語を
  「未登録」と誤判定してAI調査（`POST /api/acronym`）が走り、
  重複した解釈がINSERTされている可能性がある。NPOが2件
  （Nonprofit Organization / Non-Profit Organization、表記ゆれで
  UNIQUE制約をすり抜けている）登録されているのはこれに該当する
  可能性がある。既存レコードの棚卸し（優先順1）を行う際の確認観点
  として記録

- 検証由来の既存ゴミデータの削除（別タスク）
  `dryRun`実装前に`SYSTEM_PROMPT`検証で本番DBへ混入した検証由来の
  レコードが残っている。本タスクのスコープ外のため、削除SQLの
  提示・実行は別タスクで行う

- 検索0件が「未登録」か「異常」か区別する手段がアプリに無い
  現状、`GET /api/search`が0件を返した場合、UIは常に「未登録」と
  扱いAI調査導線を表示する。DB接続エラーやクエリ不整合等の異常時も
  同じ0件として返るため、ユーザー側から区別がつかない。`?q=`
  ディープリンクやショートカット経由の起動では特に気づきにくい。
  対策（エラー時のUI表現を分けるか等）の要否は未判断
